## Summary

- Real engines split into two families with genuinely different worst-case guarantees: **recursive backtrackers** (Perl, PCRE/PCRE2's default `pcre2_match`, Python `re`, Java `Pattern`, Ruby, classic V8 Irregexp) can take exponential or high-polynomial time on some inputs, while **automata-based engines** (Thompson-NFA simulators like RE2, Go `regexp`, Rust `regex`, Hyperscan; symbolic-derivative engines like .NET's `NonBacktracking`) guarantee time linear in `pattern.length * input.length` by construction [Cox2007; Cox2010; V8NonBacktracking; Moseley2023].
- The mechanism that makes non-backtracking matching possible is Thompson's 1968 construction plus Pike's virtual-machine formulation: compile the regex to a tiny bytecode (`char`, `match`, `jmp`, `split`, `save`) and run every live NFA thread in lock-step over the input, one character at a time, merging duplicate states so the live-thread set never exceeds the number of NFA states — this is what gives the linear-time bound [Cox2007; Cox2009; Thompson1968].
- **Catastrophic backtracking is not a bug in specific regexes so much as a structural property of unbounded recursive backtracking on ambiguous patterns.** Two production outages make the point concretely: Cloudflare's 2019 global outage was caused by a WAF rule regex containing `.*(?:.*=.*)` running through PCRE's backtracker [CloudflareOutage2019], and Stack Overflow/Stack Exchange's 2016 outage was caused by `\s+$`-style trailing-whitespace trimming hitting ~20,000 consecutive spaces, which is quadratic (`O(n²)`), not exponential, but still enough to take the site down for 34 minutes [StackOverflowOutage2016].
- **Even engines advertised as worst-case-linear can be driven to worst-case quadratic behavior** by the combination of leftmost-first match semantics and iterate-all-matches APIs: a regex like `.*[^A-Z]|[A-Z]` against a haystack of repeated capital letters forces every one of `n` per-match searches to scan to the end of the remaining haystack before backing off to the shorter alternative, for `O(n²)` total work — and this happens in RE2-style automata engines too, not just backtrackers. Hyperscan is the exception in BurntSushi's benchmark because it does not implement leftmost-first semantics at all; it reports a match as soon as it is seen [RebarQuadratic].
- Empirically, super-linear ("catastrophic" or ReDoS-vulnerable) regexes are common in deployed code, not rare curiosities: Davis, Coghlan, Servant and Lee's ESEC/FSE 2018 ecosystem-scale study found thousands of super-linear regexes across the Node.js/npm and Python/PyPI ecosystems, affecting over 10,000 modules, with anti-patterns present in over 80% of the flagged regexes [DavisEcosystem2018].
- Defenses cluster into three strategies actually used in production: (1) hard resource limits, e.g. PCRE2's `match_limit`/`depth_limit`, which bound backtracking steps and defaults to 10 million [PCRE2API]; (2) **memoization**, which Davis, Servant and Lee formalize and show can be applied selectively (not to every NFA state) to keep space overhead small, recommending an "in-degree > 1"-based selection scheme [DavisMemoization2021]; and (3) **rearchitecting the engine to be non-backtracking**, as RE2/Go/Rust do by dropping backreferences and unbounded lookaround, as V8's experimental engine does by falling back to a breadth-first NFA simulation after 50,000 backtracks, and as .NET's `NonBacktracking` mode does via symbolic derivatives that still preserve PCRE-style backtracking *semantics* [V8NonBacktracking; Moseley2023].
- **No two "PCRE-compatible" engines actually agree on feature support.** Backreferences, lookaround (and whether lookbehind must be fixed-width), atomic groups, possessive quantifiers, POSIX leftmost-longest matching and fuzzy/approximate matching are supported in different, overlapping subsets across Oniguruma, PCRE2, Python's `re` and third-party `regex`, and Java's `Pattern` — and some restrictions (e.g., Java HotSpot's lookbehind width limit) are enforced but not documented [Oniguruma; unverified: exact HotSpot lookbehind width limit and where it is enforced, since the digest material describing this only established that it is undocumented in the Javadoc, not the limit's value].
- Benchmarking regex engines fairly is itself an unsolved, actively-debated methodological problem: BurntSushi's `rebar` barometer documents its own biases at length — author/engine bias (its author also wrote the Rust `regex` crate), curation bias in which benchmarks are included, an explicit background bias toward automata-oriented engines that excludes arbitrary lookaround from measurement entirely, and an artificiality bias from repeating the same regex against the same haystack rather than varying inputs [RebarMethodology; RebarBias].

## How backtracking engines work, and why they blow up

The traditional implementation students meet first — and the one Perl, PCRE's default `pcre2_match` algorithm, Python's `re`, Java's `Pattern`, and (until recently) V8's Irregexp all use — is **recursive backtracking**: try one alternative at each choice point (a `|`, a quantifier's "match one more" vs. "stop here"), recurse, and if the rest of the match fails, undo and try the next alternative. This directly implements the regex's syntax tree as a search over possible parses of the input, which is why it is comparatively easy to bolt on features like backreferences and lookaround that have no clean automaton-based translation [Cox2007; Cox2010].

The cost is that an *ambiguous* regex — one where the same input prefix can be consumed in exponentially or polynomially many different ways by the pattern's alternatives and quantifiers — makes the backtracker explore all of them before concluding there is no match. Classic examples are nested unbounded quantifiers such as `(a*)*b` or `(a+)+b`: against a non-matching string of `a`s, the number of ways to partition the `a`s among the repetitions of the inner group grows exponentially with the string length, because none of the possible splits are pruned until the trailing `b` fails at the very end. Cox frames this as the central defect of "the standard" regex implementation: it is fast almost all of the time but has no guaranteed bound, and can effectively "never finish" on certain inputs [Cox2007].

## Thompson's construction and the Pike VM: matching without backtracking

Thompson's 1968 CACM paper showed regex matching could instead be done by compiling the expression to a nondeterministic finite automaton and simulating *all* live states simultaneously, character by character, rather than trying them one at a time with backtracking [Thompson1968]. Cox's second article recasts this as compiling the regex to a small bytecode language — instructions for consuming a literal character (`char`), matching successfully (`match`), unconditional jump (`jmp`), and a nondeterministic fork of control to two targets (`split`) — executed by a virtual machine that advances every currently-live thread by one instruction per input byte, merging any threads that land on the same program counter so that at most one thread occupies each VM instruction at a time. Because there are only as many instructions as there are regex constructs, the live-thread set is bounded by the size of the compiled program, giving `O(pattern_size * input_size)` worst-case time regardless of the input [Cox2009].

Extending this VM to record submatches (which paren group matched what) is the `save` instruction, which stamps the current input position into a slot when a thread executes it; a properly ordered scheduling of threads (Pike's contribution) recovers **leftmost-first** semantics — the same semantics Perl-style backtracking produces — rather than merely leftmost-longest, by always letting the higher-priority thread's captures win when two threads would otherwise merge at the same instruction [Cox2009]. This "Pike VM" formulation is the one BurntSushi's Rust `regex` crate and `regex-automata` implement directly for submatch extraction, described in his internals post as one strategy among several composed inside the crate's "meta" engine [BurntSushiInternals].

## DFA strategies: lazy, hybrid, one-pass, fully compiled

Simulating the NFA thread-by-thread is linear, but doing so still touches every live state on every byte. A **DFA** collapses each *set* of live NFA states into a single DFA state ahead of time, so matching becomes one table lookup per byte with no thread bookkeeping at all — at the cost that the number of distinct state sets can be exponential in the NFA size (the classic subset-construction blowup) [Cox2010].

Two practical answers to that blowup, both described in BurntSushi's regex-internals post, are used in real engines:
- A **lazy (hybrid) DFA** builds states on demand during the search and caches them, so only the state sets actually reached by real input are ever materialized; RE2 and Rust's `regex` both use this as their default fast path, falling back or clearing the cache if it grows too large (cache thrashing) [Cox2010; BurntSushiInternals].
- A **fully compiled (dense) DFA** precomputes the whole transition table ahead of time when the automaton is small enough, trading compile time and memory for the fastest possible per-byte dispatch; rebar's Cloudflare-outage benchmark demonstrates this concretely — `rust/regex` gets very high throughput on the simplified Cloudflare pattern because the pattern compiles into a full DFA, whose final `.*` state is additionally "accelerated" to a `memchr` scan for `\n` because almost all of its transitions loop back on themselves [RebarQuadraticToml — note: this quote is drawn from the analysis text of rebar's `06-cloud-flare-redos.toml` benchmark, which the digest also refers to under the general rebar-methodology material].
- A **one-pass DFA** is a further specialization for patterns whose captures can be tracked deterministically without any backtracking or thread-priority bookkeeping at all — applicable only when the NFA is unambiguous enough that at most one transition out of any state matches a given byte — giving DFA-speed submatch extraction for the subset of patterns that qualify [BurntSushiInternals].

## The "meta engine" pattern: composing multiple strategies

No single one of these strategies dominates on every regex and every task (find-vs-match, with-vs-without captures, short vs. long haystacks), so production engines increasingly **compose several internal engines and pick between them at match time**. BurntSushi's description of Rust's `regex` crate's "meta" engine is the clearest documented instance of this in the digest material: it holds a literal/prefilter layer (fast substring search via `memchr`/Two-Way, or multi-substring SIMD search via **Teddy**, ported into the Rust ecosystem from Hyperscan's work, or Aho-Corasick for larger literal sets), a lazy DFA for plain matching, a one-pass DFA and a Pike VM for submatch extraction, and a **bounded backtracker** — ordinary recursive backtracking, but only ever run on inputs small enough that its `O(pattern*input)` bit-vector-tracked visited-state memoization keeps it safe — reserved for short haystacks where its lower constant factors win [BurntSushiInternals].

Part of this composition includes **reverse-direction optimizations**: searching backward from a candidate end-of-match position (reverse-anchored, reverse-suffix, or reverse-inner search) to quickly confirm or reject candidates found by a forward literal scan. BurntSushi's internals post documents that these optimizations carry their own quadratic-blowup hazard symmetric to the forward-scan case described below, which is part of why the meta engine has fallback thresholds rather than applying them unconditionally [BurntSushiInternals].

## Quadratic blowup even in "linear" engines

A regex engine can guarantee linear time *per search* and still be quadratic in practice when a caller iterates over all non-overlapping matches in a haystack, because **leftmost-first semantics** can force each individual search to scan far past where the eventual match turns out to be. rebar's `14-quadratic.toml` benchmark demonstrates this directly with the pattern `.*[^A-Z]|[A-Z]` against a run of `A` characters: `.*[^A-Z]` is preferred by leftmost-first priority over `[A-Z]`, but because `.*` is greedy, the engine cannot know that branch fails until it has scanned to the end of the haystack; only then does it fall back and report the one-character match `[A-Z]` at the very start. Since match-iteration resumes immediately after that one-character match, this whole scan-to-the-end-then-fall-back behavior repeats at every position, yielding `O(n²)` total work for `n` characters of input — and this affects Rust's `regex`, Go's `regexp`, and other automata-oriented engines that implement leftmost-first semantics, not just backtrackers [RebarQuadratic].

The one engine in that benchmark that keeps flat, non-quadratic throughput across haystack lengths is **Hyperscan**, precisely because it does not implement leftmost-first match semantics at all: "Hyperscan doesn't implement leftmost-first match semantics... Instead, Hyperscan reports a match as soon as it is seen" [RebarQuadratic]. This is a real semantic trade-off, not a free optimization — the rebar analysis separately notes that Hyperscan reports many more (overlapping) matches on the Cloudflare regex than a leftmost-first engine would, because of its trailing `.*`, making it a poor drop-in replacement for match-count-sensitive code even though it is fast [RebarQuadraticToml].

## Hyperscan: a different contract, and how it stays fast

Hyperscan (Intel; NSDI 2019) targets multi-pattern matching for network intrusion detection and similar workloads, and is built around **decomposing each regex into a "string" component and a residual finite-automaton component**, then matching the string component with a highly parallel SIMD literal matcher and the automaton residual with bit-parallel NFA simulation over the SIMD-matched positions [HyperscanNSDI19]. This decomposition strategy is what lets Hyperscan avoid full backtracking (or full DFA blow-up) on the kinds of patterns network-security rule sets actually contain, while also explaining why it reports matches eagerly rather than honoring leftmost-first priority, as noted above [HyperscanNSDI19; RebarQuadratic].

Hyperscan's multi-substring literal matching draws on the same lineage as classical multi-pattern string search — Aho-Corasick's finite-state keyword machine [AhoCorasick1975] and Boyer-Moore-style skip search [BoyerMoore1977] — extended with SIMD; the **Teddy** algorithm that Rust's `regex` crate later adopted for its own literal prefilters is explicitly a port of a Hyperscan technique [BurntSushiInternals].

## Submatch extraction: tagged NFAs and match-semantics choices

Extracting *which* substring matched *which* capture group — not just whether the whole pattern matched — requires more machinery than plain acceptance. Laurikari's SPIRE 2000 paper introduces **tagged NFAs (TNFAs)**: NFA transitions are annotated with "tags" that record input positions, and the paper shows how to convert a TNFA to a **tagged DFA (TDFA)** so that capture-group tracking can be done with DFA-speed matching rather than falling back to backtracking or thread simulation for every search [Laurikari2000]. Laurikari's paper also addresses a correctness point about lookahead operators relative to classic lexer generators (Lex/Flex): TNFA-based construction gets lookahead-operator semantics right in cases where those tools' longest-match, tag-free automata do not [Laurikari2000].

This submatch machinery is also where the **POSIX leftmost-longest vs. Perl/PCRE leftmost-first** distinction becomes concrete: POSIX regex semantics require the overall match, and each subgroup, to be the *longest* possible at each choice point, evaluated independently of which alternative in the pattern produced it, whereas Perl-style engines (backtracking or Pike-VM-based) resolve ambiguity by *priority order* — whichever alternative the pattern lists first, or whichever quantifier greediness dictates, wins, regardless of whether a longer match was available from a lower-priority branch [Cox2009; Laurikari2000].

## Defenses against catastrophic and super-linear backtracking

Three distinct mitigation strategies show up across real engines and the literature:

**Hard resource limits.** PCRE2 exposes `pcre2_set_match_limit()`, which caps the number of times `pcre2_match()`'s main matching loop can iterate; once the counter is exceeded the function returns `PCRE2_ERROR_MATCHLIMIT` rather than continuing to backtrack indefinitely. Its default is ten million iterations, described as handling "all but the most extreme cases," and a companion `pcre2_set_depth_limit()` bounds recursion depth for engines/configurations where stack (not counter) exhaustion is the risk; both limits also apply, differently, to `pcre2_dfa_match()` [PCRE2API]. This is a blunt instrument — it converts a hang into an error — but it is the mitigation actually deployed by default in a widely used C library.

**Selective memoization.** Davis, Servant and Lee's IEEE S&P 2021 paper formalizes memoized backtracking (a "Memoized NFA," building on Cox's suggestion that a 32 KB memoization budget is a reasonable target [DavisMemoization2021, citing Cox]) and studies *which* NFA states are worth memoizing rather than memoizing all of them, since naive full memoization can itself blow out memory. They propose selection schemes such as memoizing states with in-degree greater than one (`Qin-deg>1`) or memoizing only "ancestor" states of the pattern's ambiguity (`Qancestor`), and show a run-length-encoded (RLE) memo-table representation is effective for the common case of "catch-all" visit vectors. Their own empirical corpus analysis found regexes containing backreferences typically use few distinct backreferenced groups (98% use three or fewer) and mostly fixed-width capture groups (78%), meaning most real backreference usage has low-polynomial rather than exponential worst-case cost, so selective memoization is a tractable general-purpose fix even for backreference-supporting engines [DavisMemoization2021].

**Rebuilding the engine to be non-backtracking, or falling back to one.** Three different real implementations of this are documented:
- **RE2 / Go `regexp` / Rust `regex`** simply do not support backreferences or unbounded-width lookaround, by design, because supporting them would reintroduce super-linear worst cases; this is the tradeoff Cox argues for directly [Cox2010].
- **V8's experimental engine** (shipped starting in V8 8.8) runs the standard backtracking Irregexp engine first, but falls back to a separate non-backtracking engine — described as based on "breadth-first traversal of the automaton," i.e., a Thompson/Pike-style simulation, credited explicitly to Cox's articles and to RE2/Rust `regex` — once a configurable backtrack-count threshold (`--regexp-backtracks-before-fallback`, default 50,000) is exceeded. The fallback is only legal when the pattern contains no backreferences, no lookaround, and no large/deeply nested finite repetitions, and does not have the Unicode or case-insensitive flags set; V8's own documentation states plainly that backreferences and lookaround "cannot be supported without major changes that alter asymptotic worst-case complexity." A non-standard `l` ("linear") regex flag lets a program opt a pattern into the non-backtracking engine unconditionally, throwing at construction time if the pattern isn't supported, with the guarantee stated as `O(pattern.length * input.length)` [V8NonBacktracking].
- **.NET's `NonBacktracking` mode** (from .NET 7) takes a different route: **symbolic derivatives**, formalized in Moseley et al.'s PLDI 2023 paper as derivatives based on *locations in words* rather than individual characters, which is what let the technique support anchors (`^`, `$`, `\b`) — a known gap in earlier derivative-based approaches — while still preserving PCRE-style backtracking match *semantics*, not just acceptance. The paper reports a formal proof of correctness (which the authors describe as the first for an industrial regex matcher of this kind) and states that developing it surfaced pre-existing bugs in other engines: cases where "state-of-the-art algorithms were semantically incorrect, inefficient (superlinear complexity), or excessively restrictive" [Moseley2023].

## Two real-world outages as case studies

**Cloudflare, 2 July 2019.** A single Web Application Firewall rule contained the regex `(?:(?:\"|'|\]|\}|\\|\d|(?:nan|infinity|true|false|null|undefined|symbol|math)|\`|\-|\+)+[)]*;?((?:\s|-|~|!|\{\}|\|\||\+)*.*(?:.*=.*)))`, which Cloudflare's own postmortem identifies as creating "excessive backtracking" and directly names as the cause of CPU exhaustion underlying a 27-minute global outage [CloudflareOutage2019]. rebar's curated benchmark isolates the specific pathological fragment as `.*(?:.*=.*)`, simplified further to `.*.*=.*`, and reproduces the appendix analysis from Cloudflare's own postmortem; it notes this regex was originally deployed in a "is a match / not a match" firewall context, which matters because several automata engines (RE2, Rust `regex`, Go `regexp`) do *not* exhibit the pathological behavior on this pattern, only PCRE-style backtrackers do, because the fully-compiled/lazy-DFA engines maintain roughly constant throughput regardless of haystack length while the backtracker's runtime blows up with haystack size [CloudflareOutage2019; RebarQuadraticToml].

**Stack Overflow / Stack Exchange, 20 July 2016.** A 34-minute outage was traced to the regex `^[\s‌]+|[\s‌]+$`, intended to trim Unicode whitespace from the start and end of a line, hitting a malformed post containing roughly 20,000 consecutive whitespace characters. The postmortem gives the exact mechanism and arithmetic: for a simplified pattern like `\s+$` against `20,000` non-terminal spaces, the backtracker tries matching starting at the first space (checking all 20,000 remaining characters), fails, backtracks to the second space (checking 19,999), fails, and so on, performing `20000 + 19999 + 19998 + ... + 1 = 199,990,000` character-class checks — the postmortem explicitly flags this as **`O(n²)`, not exponential**, i.e., "not classic catastrophic backtracking," yet still enough to take the load-balancer health check (served from the affected home page) down and make the entire site unreachable. The regex was subsequently replaced with a plain substring/trim function [StackOverflowOutage2016].

These two incidents are useful as a teaching pair precisely because they are qualitatively different failure classes with the same visible symptom (CPU-bound outage from a regex): one genuinely combinatorial/exponential-flavored (Cloudflare's nested-alternation-plus-`.*` pattern), one "merely" quadratic (Stack Overflow's anchored `\s+$`) — underscoring that *any* super-linear worst case, not only exponential ones, is a viable denial-of-service vector once an attacker (or an unlucky user post) controls the input length [StackOverflowOutage2016; DavisEcosystem2018].

The digest's engine-documentation survey shows meaningful, undocumented-in-places divergence in which extended features an engine supports, even among engines that market themselves as PCRE-compatible:

Java's `Pattern` supports possessive quantifiers, atomic groups, backreferences and lookahead/lookbehind, but its lookbehind is width-restricted by the HotSpot implementation in a way that is **not documented in the `Pattern` Javadoc itself** — a real "undocumented limit" gap worth flagging to students, though the digest material only established the existence and undocumented nature of the restriction, not its exact numeric bound, which is why this file states no specific number [unverified: exact HotSpot lookbehind width limit].

V8's classic Irregexp engine supports the full standard-plus-extensions JavaScript regex feature set (backreferences, lookaround, etc.); its experimental non-backtracking engine, as detailed above, supports none of those, which is precisely why it is opt-in via the `l` flag or a bounded fallback rather than the default [V8NonBacktracking].

## Benchmarking regex engines, and why it is hard

BurntSushi's `rebar` project ("regex barometer") is the most methodologically self-aware regex benchmark documented in the sourced material, and it is explicit that no regex benchmark is neutral. Its stated design goals are to support flexible workload types (not just "does it match," but capture-group extraction, grep-style line iteration, and compile time as a separate measurement from search time), to make adding new engines and benchmarks cheap, and to report results that are robust to noise — it uses the median across runs for single-benchmark results (chosen because many engines, e.g. Rust's lazy-DFA-based `regex`, are deliberately slower on their first pass while part of the DFA is still being constructed) and the **geometric mean of per-benchmark speedup ratios** to summarize an engine's standing across the whole suite [RebarMethodology].

Its `BIAS.md` document lists biases the author identifies in his own tool, which is itself a useful teaching artifact about benchmark methodology in general:
- **Author/engine bias** — the barometer's author also wrote the Rust `regex` crate being benchmarked, and acknowledges this "should perhaps be treated suspiciously," including the possibility of unconsciously selecting benchmarks he has tuned for.
- **Curation bias** — any curated benchmark set implies inclusion/exclusion decisions that cannot fully represent "all regexes used in the wild."
- **Analysis bias** — the written analysis for each benchmark is "heavily geared towards the `rust/regex` engine" because the author understands that engine's internals best and finds most other engines' source code difficult to casually read.
- **Model bias** — the benchmark models used (count, grep, compile, capture-extraction) cannot capture every real usage pattern; notably absent is the common production technique of running a cheap, over-approximate regex first and a precise one second to filter false positives, and a combined compile+search model is deliberately excluded in favor of measuring compile and search separately.
- **Feature-scope bias** — because the author's background is in automata-oriented engines, the barometer's regexes deliberately avoid features "not known how to implement efficiently," such as arbitrary lookaround (only simple anchors like `^`, `$`, `\b` are used), meaning entire classes of real-world regexes are simply never measured.
- **Repetition-artificiality bias** — the `count` and `compile` benchmark models repeat the identical regex against the identical haystack many times, which does not resemble typical real-world usage (where the haystack usually varies) and can make especially well-tuned JIT or caching mechanisms look artificially good [RebarBias].

## Course design notes

**What is teachable here, and its dependencies.** This file assumes students already have Thompson-construction NFA and DFA-conversion machinery from `regex/01-theory-and-constructions.md` (cross-reference); the payload here is the *engineering* layer on top of that theory: why real engines don't just implement "the" textbook algorithm, why backtracking is still dominant despite its bad worst case, and how production systems actually bound or avoid the bad case. A natural class sequence is: (1) recursive backtracking and why it is easy to build but has no time bound, using the two outage case studies as motivation; (2) Thompson/Pike VM as the alternative with an actual complexity guarantee; (3) the DFA family (lazy/hybrid, one-pass, full) as a further speed layer once determinism is available; (4) the "meta engine" idea that real systems don't pick one of these, they pick among them per-query. Rough time: two to three lectures — one for backtracking + the outages (very motivating, low prerequisite), one for Thompson/Pike VM construction (this needs the automata theory from `01-theory-and-constructions.md` already in hand), and optionally one for the meta-engine/DFA-strategy material and the ReDoS-defense landscape, which is more of a "systems tour" than new theory.

**Concrete exercise idea.** Give students the Cloudflare regex fragment `.*(?:.*=.*)` and the Stack Overflow regex `\s+$`, plus a small backtracking regex engine (or Python's `re` with a step counter patched in, or `re.match` timed against exponentially-growing crafted inputs). Have them (a) empirically measure blowup as input length grows for both patterns, (b) classify each as exponential vs. quadratic from the growth curve, and (c) rewrite each pattern to remove the ambiguity (e.g., replace nested `.*` with a possessive/atomic equivalent, or replace `\s+$` with a reverse-scan/substring approach) and re-measure. This directly exercises the summary's central claim that "catastrophic" isn't one phenomenon.

**Misconceptions students arrive with.**
1. That "regex" names one algorithm — in reality, even engines that look similar from the outside (PCRE2 has *two*, `pcre2_match` and `pcre2_dfa_match`, with different semantics and different guarantees) may implement fundamentally different matching strategies [PCRE2API].
2. That avoiding backreferences and lookaround is enough to make a regex "safe" — the quadratic leftmost-first blowup shown by rebar's `.*[^A-Z]|[A-Z]` benchmark uses no extended features at all and still produces `O(n²)` behavior when matches are iterated, even on some automata-based engines [RebarQuadratic].
3. That "exponential blowup" is the only shape catastrophic backtracking takes — the Stack Overflow incident is explicitly documented as quadratic, not exponential, and was still severe enough to cause an outage [StackOverflowOutage2016].
4. That a "linear time" engine guarantee (RE2, Go, Rust `regex`) means *any* usage pattern of that engine is safe — the guarantee is per-search; API usage patterns (iterating all matches) can still produce quadratic *aggregate* time [RebarQuadratic].
5. That regex benchmarks are neutral measurements — `rebar`'s own bias documentation is a good antidote and a rare example of a benchmark author publishing a bias statement at all [RebarBias].
